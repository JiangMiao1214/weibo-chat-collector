# 从 0 到完成的实施步骤

## 总体路线

项目按“先可用、再自动化、后增强”的顺序推进。

首版不把微博自动采集写死，而是先完成稳定的数据底座：

- 多微博账号。
- 多群聊。
- 同一个数据库。
- 时间段采集任务模型。
- 手动导入。
- 全员消息归档。
- 图片、文件、链接附件保存。
- 搜索筛选。
- 批量删除。

微博自动采集作为可插拔适配器实现，等两个微博号实机验证通过后接入。

## 第 0 步：确认项目边界

目标：把无法靠代码猜出来的信息确认清楚，避免后面返工。

需要确认：

- 微博账号 A 的备注名。
- 微博账号 B 的备注名。
- 账号 A 对应的群聊名称。
- 账号 B 对应的群聊名称。
- 首次测试采集的时间段，例如最近 1 天或最近 7 天。
- 附件存储位置，建议放在项目目录下的 `data/attachments`。
- 批量删除默认采用软删除，确认后再做彻底清理。
- 是否接受首版先通过 JSON/CSV 导入跑通完整流程。

产出：

- 账号和群聊配置清单。
- 首次测试时间范围。
- 附件保存策略。
- 删除策略。

## 第 1 步：初始化项目骨架

目标：建立可以长期开发的项目结构。

建议结构：

```text
weibo-chat-collector/
  backend/
  frontend/
  data/
    attachments/
    imports/
  docs/
  scripts/
  README.md
```

需要做：

- 初始化后端项目。
- 初始化前端项目。
- 增加 `.env.example`。
- 增加本地运行说明。
- 增加数据库目录和附件目录。

推荐技术：

- 后端：Python FastAPI。
- 数据库：SQLite。
- 前端：React + Vite。
- 图表后续再接入 ECharts。

产出：

- 后端能启动。
- 前端能启动。
- 项目目录结构清楚。

## 第 2 步：落地数据库模型

目标：先把数据存储设计稳定。

需要建表：

- `weibo_accounts`
- `chat_groups`
- `chat_users`
- `group_members`
- `messages`
- `attachments`
- `collection_jobs`
- `deletion_jobs`
- `import_batches`

需要做：

- 建立数据库迁移。
- 建立基础索引。
- 建立消息去重规则。
- 建立软删除字段。
- 建立附件关联规则。

产出：

- 本地 SQLite 数据库。
- 数据表可创建、可重建。
- 有一份初始化脚本。

## 第 3 步：做手动导入

目标：即使微博自动采集还没验证，也能先让系统完整跑起来。

需要支持：

- JSON 导入。
- CSV 导入。
- 导入时选择账号和群聊。
- 自动创建用户。
- 自动创建附件记录。
- 重复消息跳过。
- 红包消息过滤。

建议先定义统一导入格式：

```json
{
  "account": "account-a",
  "group": "group-a",
  "messages": [
    {
      "source_message_id": "msg-001",
      "sender_name": "用户昵称",
      "sent_at": "2026-06-10 21:00:00",
      "message_type": "text",
      "content_text": "消息内容",
      "attachments": []
    }
  ]
}
```

产出：

- 可以导入测试数据。
- 数据能进入数据库。
- 重复导入不会重复入库。

## 第 4 步：做消息列表和搜索

目标：让归档数据能被查看和检索。

需要做：

- 消息列表接口。
- 消息详情接口。
- 账号筛选。
- 群聊筛选。
- 用户名筛选。
- 日期范围筛选。
- 关键词搜索。
- 消息类型筛选。
- 是否包含附件筛选。

前端页面：

- 左侧筛选区。
- 右侧消息列表。
- 消息详情抽屉或详情页。
- 附件入口。

产出：

- 能查到某个账号、某个群聊、某个时间段的消息。
- 能通过关键词找到消息。

## 第 5 步：做附件保存

目标：支持图片、文件、链接。

需要做：

- 图片附件表结构入库。
- 文件附件表结构入库。
- 链接附件表结构入库。
- 附件本地路径管理。
- 附件下载状态。
- 附件哈希去重。

首版策略：

- 图片和文件先支持本地保存或手动导入本地路径。
- 链接先保存 URL、标题、展示文本。
- 自动下载可放在采集适配器验证后做。

产出：

- 消息能关联附件。
- 附件能预览或打开。
- 附件不会和消息正文混在一起。

## 第 6 步：做批量删除

目标：满足后续清理聊天记录的核心需求。

需要做：

- 删除预览接口。
- 删除执行接口。
- 按账号删除。
- 按群聊删除。
- 按时间段删除。
- 按用户删除。
- 按消息类型删除。
- 按搜索结果删除。
- 按采集批次删除。
- 是否同时删除附件。

默认策略：

- 先软删除。
- 删除前显示数量预览。
- 删除前二次确认。
- 后续再做彻底清理。

产出：

- 可以安全批量删除。
- 删除后搜索结果不再显示。
- 必要时可以恢复软删除记录。

## 第 7 步：做时间段采集任务框架

目标：先把“用户选择时间段采集”的产品流程做好。

需要做：

- 创建采集任务。
- 选择账号。
- 选择群聊。
- 选择开始时间和结束时间。
- 展示任务状态。
- 展示新增、跳过、失败数量。
- 预留不同采集适配器。

该阶段最初不要求真正连接微博；任务框架现已完成，并已接入后台 API 采集器。

产出：

- 前端可以创建时间段采集任务。
- 后端可以记录任务状态。
- 微博 API 采集器可以在该任务框架内后台执行（现已接入）。

## 第 8 步：微博采集实机验证

目标：确认两个微博号到底能用哪种方式获取历史群聊数据。

需要验证：

- 账号 A 能否稳定登录。
- 账号 B 能否稳定登录。
- 账号 A 能否查看群聊 A 的历史消息。
- 账号 B 能否查看群聊 B 的历史消息。
- 页面是否能按时间加载历史消息。
- 图片是否能访问。
- 文件是否能下载。
- 链接是否能读取。
- 红包消息是否有稳定特征可过滤。
- 小范围辅助采集是否触发验证或风控。

产出：

- 可行采集方式结论。
- 采集限制说明。
- 微博采集适配器实现方案。

## 第 9 步：接入微博采集适配器

目标：把验证过的微博数据获取方式接到时间段采集任务。

需要做：

- 实现账号会话管理。
- 实现群聊历史消息读取。
- 实现按时间段停止条件。
- 实现消息解析。
- 实现附件解析。
- 实现红包过滤。
- 实现入库。
- 实现失败后停止并由用户人工续传；不做自动重试。
- 实现全局低频率、可安全停止的串行采集。

产出：

- 选择时间段后可以自动采集对应群聊消息。
- 两个账号的数据能进入同一个数据库并正确区分。

## 第 10 步：完善体验和稳定性

目标：让项目可以长期使用。

需要做：

- 错误提示。
- 空状态。
- 加载状态。
- 数据备份。
- 导出。
- 日志页面。
- 上下文查看。
- 统计仪表盘。

产出：

- 可长期运行的本地应用。

## 当前落点

第 0–9 步的基础结构、导入、消息管理以及微博 API 采集主链路已经落地。当前重点是第 10 步中的真实小范围验证、备份/导出和长期运维体验；手机端接口研究继续后移。真实验证应从一个账号、一个群和较短时间范围开始，且不改变“所有错误零自动重试、人工续传”的风控策略。
