## TEST-001：历史补采集效率低，需频繁人工续传

- **发现日期**：2026-10-20。
- **入口**：消息 → 查看引用原文 → 原文未在本地找到 → 创建有界补采集任务。
- **状态**：待优化，尚未修改分页起点或补采集页数策略。
- **影响**：目标时间距离最新消息较远、期间消息较多时，需要读取大量范围外消息，并反复人工续传才能接近目标时间。

### 测试现象

用户希望采集 **2026-09-05 00:00:00 至 2026-09-08 18:33:00** 的数据，但截图中任务 #13 的实际回溯进度为：

1. 第一次运行从游标 `0` 开始；读取 6 页后，当前最早消息仍为 **2026-10-20 13:00:53**，看到 120 条，新增 0 条。
2. 每次运行到 20 页自动停止，停止码为 `page_limit`，提示 `Stopped after the per-run page limit (20).`。
3. 人工续传后，第二次运行再读取 20 页；累计 40 页、看到 800 条、新增 0 条，最早消息为 **2026-10-17 14:48:53**，仍未到达目标日期。

以上来自用户提供的测试截图，不代表任务之后的实时状态。

### 已确认的原因与边界

- 新任务的初始游标为 `max_mid=0`，当前实现从最新消息逐页向历史回溯，没有直接定位所选日期的逻辑。
- 所选开始、结束时间用于消息入库过滤，不等于远端分页的起点。范围外消息会被读取并计入“看到”，但不会入库；因此此次“新增 0”与尚未到达目标日期一致。
- 补采集入口将任务的 `recovery_max_pages` 设置为 `20`。执行时取此限制与全局页数上限的较小值，所以仅提高全局页数上限不能解除该任务的 20 页限制。
- 该停止属于项目自身的单次运行页数限制，不能据此认定微博报错或目标范围已采集完成。
- 沿断点续传会保留原任务、累计进度和已提交游标，继续向更早消息翻页；截图中的第二次运行并非重新从最新消息开始。
- 前面的“日期 + 小时 + 分钟独立选择、12 行列表”修复只涉及输入控件，没有改变以上采集策略。

### 期望行为与待评估方向

1. 历史采集应尽可能减少为到达目标时间而重复读取较新消息的请求。评估能否利用同账号、同群的可靠历史游标或消息标识定位起点；必须证明不会漏采，不能凭日期猜测游标，也不能假定远端支持日期跳转。
2. 评估适合历史补采集的单次页数策略，减少每 20 页手动操作的负担，同时保留请求节流、风险冷却、错误停止和人工启动确认。
3. 监控页明确区分“正在回溯至目标日期”和“已进入目标时间范围”，解释范围外读取与新增条数的关系。
4. 达到页数上限时，用中文说明停止原因、已到达的时间和续传方式，避免被误认为异常或完成。

### 后续验收要点

- 使用隔离数据库、模拟接口和假 Cookie 验证，不以真实在线采集充当自动化测试。
- 起点优化不能跨账号、跨群或跳过目标范围内的消息；无法确认可靠起点时应有明确的回退行为。
- 只有目标时间范围内、通过过滤且未重复的消息入库。
- 页数限制与界面说明一致；范围未覆盖完整不能标记为完成。
- 停止及续传保留原任务与已提交页事务、游标、去重结果；既有账号保护机制继续生效。
- 界面能解释“看到很多条但新增为 0”和因页数上限停止的含义。

## TEST-002：账号管理缺少删除账号功能

- **发现日期**：2026-10-21。
- **入口**：账号管理 → 账号卡片。
- **状态**：2026-10-21 已实现，仅允许删除无历史数据的本地账号；本轮没有删除真实账号。
- **影响**：测试占位账号或不再使用的账号，即使停用后仍保留在管理列表，无法通过界面删除。

### 测试现象与现有边界

用户提供的截图中，已停用的占位账号卡片提供“编辑账号”“登录与采集”“查看账号消息”“清除登录凭据”，没有“删除账号”入口。该账号显示有 1 个关联群、0 条未删除消息；这个数量不能证明回收站、任务记录或附件等关联数据全部为空。

[账号与群聊管理说明](target-management.md)明确：停用保留历史，清除登录凭据只清除该账号本机 Cookie，不会删除账号、群或历史消息。因此这两项操作不能替代用户需要的删除账号功能。

### 期望行为与待明确范围

1. 在账号管理提供“删除账号”入口，能够清理不再需要的本地账号记录；不涉及注销微博平台账号。
2. 删除前展示目标账号与受影响内容，并要求明确确认，取消时不做修改。
3. 原记录要求实施前明确关联数据规则。2026-10-21 用户已确认仅删除无历史数据的账号，空群及本机凭据可随之删除，其余关联记录均阻止删除，磁盘原件保留。
4. 明确有运行中采集、扫码会话、归档或 OCR 工作时的处理方式，避免删除过程中后台继续写入。

### 后续验收要点

- 使用隔离数据库、假凭据和模拟任务，覆盖空账号、有关联群的账号、有历史或回收站数据的账号。
- 预览范围与最终执行范围一致；未经确认或取消操作不得删除。
- 删除只影响指定账号及明确纳入范围的关联内容，不影响其他账号的数据、凭据或共享原件。
- 运行中任务的处理符合最终确定的规则，失败时不留下无法恢复的部分删除或悬空关联。
- 成功后刷新账号列表及相关选择器，清除失效的当前选择，不再出现已删除账号。
- 原记录时未执行功能测试；本轮已补隔离测试，真实删除未运行。证据见下方本轮验收。

### 已确认方案与实现（2026-10-21）

- 用户确认采用保守删除：账号可没有群，也可关联空群；正常/回收站消息、附件、群成员、采集任务及断点、导入、网页快照、验证/删除记录、归档设置/任务/主机记录、OCR 设置/任务/文字结果或操作日志任一存在，均拒绝删除。
- “删除账号”先读取独立预览，展示账号、空群、凭据及阻止原因；只有可删除时才允许明确确认。取消不写入，失败后必须重新预览。
- 执行在数据库写锁内重新检查全部范围和预览指纹；更名、空群变化、凭据变化、新历史记录或新扫码会话都会阻止旧确认。正常凭据上传也先取得写锁并检查账号，避免删除后写回凭据。
- 只清除指定账号及其空群、标准本机凭据文件；不读取凭据内容到响应或日志，不跟随凭据符号链接，不碰磁盘原件。数据库或凭据清理异常回滚；数据库提交失败时恢复内存中暂存的凭据。
- 有运行采集、在途归档/OCR 的账号必然包含关联记录，保持不动；扫码会话另行阻止。成功后刷新列表及消息/采集/验证选择器，失效账号和群不再保留。

## TEST-003：一个账号只能对应一个群聊

- **提出日期**：2026-10-21。
- **入口**：账号管理、群聊管理、登录绑定及采集目标配置。
- **状态**：2026-10-21 已实现，新配置限制一账号一群；已有多群保留并提示待整理。
- **明确需求**：一个账号对应一个群聊，不能对应两个或多个群聊。

### 当前情况与期望行为

原[账号与群聊管理说明](target-management.md)允许一个账号新增多个群，现已按本条用户要求同步修订。

1. 配置完成的账号只对应一个群聊。已有群聊的账号不能再新增或绑定第二个群聊；不能通过停用已有群聊绕过这一限制。
2. 群聊管理、扫码绑定、高级工具/数据导入等配置入口执行一致的规则，后端同时校验，避免绕过界面或并发请求产生多群关联。
3. 采集目标、账号卡片及相关选择器按账号对应的唯一群聊展示，账号之间的消息、凭据和任务继续隔离。

### 用户已确认的兼容处理（2026-10-21）

- 新账号可暂时无群，卡片显示“待配置群聊”，不用同时创建群。
- 已有多群账号保留全部关联、历史和断点，提示“待整理”；禁止新增群或变更远端绑定，允许资料维护、原目标查询与采集。不会自动挑选保留项、删除、合并或迁移。已有历史的群仍不能改绑，另行整理须单独确定方案。
- 本次明确的是每个账号的群聊数量限制，不额外推定“同一个微博群不能由不同账号分别配置”。

### 后续验收要点

- 首个群聊可正常配置；同一账号新增或绑定第二个群聊时，前后端均拒绝并给出明确提示。
- 并发创建、停用群聊、备用配置及导入入口不能绕过限制。
- 不同账号可各自配置一个群聊，查询、采集、续传与删除范围不串数据。
- 既有多群数据按确认后的兼容方案处理，不能静默丢失历史或破坏关联。
- 原记录时功能及迁移测试未运行；本轮已补隔离测试和重跑迁移不改旧多群的回归，不执行真实数据迁移。

### 实现与隔离边界

管理新增、备用目标配置和 JSON/CSV 导入共用群数量检查，在 SQLite 写事务中检查并写入，停用群仍计数；并发请求只允许首个群成功。管理编辑、备用编辑与扫码确认共用绑定保护。前端新增选项禁用已有群账号，唯一群随账号卡片进入采集，旧多群显示提示并限制绑定输入。另修复账号卡片跳转后状态刷新复用旧账号目标的问题：明确把卡片目标传给刷新，保持所选账号和唯一群。导入既有同名群仍正常工作，不因旧多群兼容而丢弃历史。数据库关系结构保留兼容，未新增会使旧多群升级失败的唯一索引。

## TEST-004：小时分布仅在选择日期后显示

- **提出日期**：2026-10-21。
- **入口**：消息页 → 日期筛选与小时分布。
- **状态**：2026-10-21 已实现，按实际生效日期决定显示，清除日期同步清除小时。
- **明确需求**：没有筛选日期时不显示按小时分布的选项，只有选择日期后才显示。

### 测试现象

用户反馈，在未启用日期筛选时，页面仍显示“小时分布”、00–23 时的统计与筛选选项及“清除小时”按钮，占用消息阅读空间。截图中日期输入框显示日期文字；是否显示小时分布应以实际生效的日期筛选为准，不能仅根据输入框展示文字判断。

### 期望行为

1. 未选择日期或点击“全部日期”后，隐藏整个小时分布区域，包括标题、小时统计/选项及“清除小时”按钮，不保留空白占位。
2. 选择日期并使筛选生效后，显示对应日期的小时分布，支持按小时进一步筛选消息。
3. 清除日期时同步清除已选小时，防止界面已隐藏小时选项、请求却仍带小时条件。此项作为配套交互要求，避免隐藏筛选影响结果。
4. 切换日期后刷新小时统计，不展示上一日期的过期结果；其他消息类型、成员及正文查找等控件仍按原有规则使用。

### 后续验收要点

- 初始无日期筛选及“全部日期”状态下，小时分布区域不可见且不占空间。
- 选定日期后才出现小时分布，统计与实际日期范围一致。
- 已选日期和小时后清除日期，小时条件随之清除；列表、导出和删除预览均不能残留隐藏的小时筛选。
- 快速切换日期时，旧请求的迟到响应不能覆盖新日期统计。
- 原记录时未运行功能测试；本轮已补模拟数据交互回归与完整验收，见下方证据。

### 实现与交互

小时区以 `appliedFilters` 的日期边界为准；任一日期边界生效即显示（保持高级跨天/单边范围的累计口径），仅输入日期草稿不显示。全部日期、清空顶部日期和高级日期全部清空后搜索均移除小时；查询与 JSON 请求序列化也统一规范化，列表、正文查找、导出、删除/恢复预览和执行不带隐藏小时。切换日期立即撤下旧统计，现有请求身份与取消保护继续阻止迟到响应覆盖。

## TEST-005：按附件条件彻底删除会删掉附件却留下消息

- **发现日期**：2026-10-21。
- **入口**：回收站 → 附件条件筛选 → 预览彻底删除 → 确认彻底删除；对应 `POST /api/messages/hard-delete`。
- **类型/优先级**：Bug / P1，数据一致性问题。
- **状态**：已修复，隔离 HTTP 回归通过；未操作真实消息或磁盘原件。

### 最小复现与实际表现

1. 在隔离库建立账号 1、群 11 的已删除消息 `id=4`，附一条标题为“甲删除附件”的附件；另建账号 2 的已删除消息及账号 1 的正常消息作为隔离对照。
2. 使用以下范围读取 `hard-delete-preview`，再将同一范围连同 `confirm=true` 提交到 `hard-delete`：

   ```json
   {"filters":{"account_id":1,"group_id":11,"has_attachment":true},"confirm":true}
   ```

3. 预览返回 1 条消息、1 条附件。执行返回 HTTP 200，结果却是 `preview_count=1`、`deleted_count=0`、`attachment_record_count=1`。
4. 查库确认：消息 4 仍在回收站，关联附件已变成 0 条；因此再次按“有附件”筛选时，这条残留消息也不再可见。其他账号和正常消息保持不变。
5. 把 `has_attachment` 换成仅命中附件标题的 `keyword="甲删除附件"`，同样复现。将消息类型设为 `text`、附件类型设为 `image`，使用 `viewer={"media":"photos"}` 也同样复现。
6. 对照：仅按账号和群筛选时，预览与执行均删除 1 条消息及 1 条附件，测试通过。

### 原因、影响与修复方向

- 已确认原因：[hard_delete_messages](../backend/app/api/messages.py) 第 627–655 行将同一个动态筛选子查询先后用于附件、搜索索引和消息删除。第一步删除附件后，`EXISTS attachments`、附件关键词或附件媒体条件不再成立，后续步骤重新计算得到空范围。事务仍成功提交，产生“附件已删、消息未删”的部分业务结果。
- 影响范围是依赖附件内容匹配的彻底删除；不是所有删除都失败。可导致附件元数据丢失、回收站残留及预览/结果不一致。此次测试没有生成或删除磁盘原件。
- 建议在同一写事务中先固定符合条件的消息 ID 集合，后续关联记录与消息删除全部使用该集合；任一步失败应整体回滚，避免在删除附件后重算范围。
- 验收应覆盖有附件条件、附件标题/文件名/URL 关键词、仅附件命中的图片/视频/链接条件，以及其他账号、正常消息和磁盘原件保持不变；执行数量应与事务内固定集合一致。
- 关联契约：[消息 API](message-api.md)、[回收站](recycle-bin.md)。额外诊断的三种筛选均因 `deleted_count: 0 != 1` 失败。

### 修复结果（2026-10-21）

`hard_delete_messages` 在写事务内先固定命中消息 ID 到连接内临时表，附件、搜索索引和消息删除共用该集合；异常由连接事务整体回滚。没有动态 SQL 参数数量限制导致的大批量 ID 展开；测试覆盖 1501 条目标和空范围。数据库 schema 与磁盘原件策略不变。

新增正式回归 [test_hard_delete_snapshot.py](../backend/tests/test_hard_delete_snapshot.py)：10 项通过，包含附件存在、标题/文件名/URL、图片/视频/链接、三步故障回滚、其他账号/正常消息及原件保留。附件筛选 7 项先看到 `deleted_count=0`，实现后全部通过；原本正确的普通删除和回滚行为补绿灯回归。

## TEST-007：已知 UID 被同名无 UID 用户吸收，可能误判重复

- **发现日期**：2026-10-21。
- **入口**：JSON/CSV 导入的用户识别与去重；采集入库也共用 `ensure_user`，但本轮没有运行真实采集。
- **类型/优先级**：Bug / P2，成员身份错误，特定条件下漏导消息。
- **状态**：已修复，临时 JSON/CSV、数据库和模拟采集入库回归通过。

### 最小复现与实际表现

在一个空隔离库内导入下列三条消息，账号/群可取“模拟账号”/“模拟群”；三条均不提供 `source_message_id`：

```json
[
  {"sender_name":"模拟同名成员","sent_at":"2026-10-01 10:00:00","message_type":"text","content_text":"离线旧消息"},
  {"sender_name":"模拟同名成员","source_user_id":"uid-a","sent_at":"2026-10-01 11:00:00","message_type":"text","content_text":"同秒相同正文"},
  {"sender_name":"模拟同名成员","source_user_id":"uid-b","sent_at":"2026-10-01 11:00:00","message_type":"text","content_text":"同秒相同正文"}
]
```

- 期望：`uid-a` 与 `uid-b` 是两个已知不同用户，两条同秒同文消息均保留；总计导入 3 条，重复 0 条。
- 实际：`chat_users` 只有一个 `source_user_id=NULL` 的用户，后续两个 UID 都复用了该 `user_id`；结果 `inserted_count=2`、`duplicate_count=1`，第二个 UID 的消息被静默跳过。
- 失败断言：`inserted_count: 2 != 3`，不是格式错误或数据库异常。

### 原因、影响与修复方向

- 已确认原因：[ensure_user](../backend/app/importer.py) 第 179–217 行：按 `source_user_id` 查不到记录后，即使当前消息已带明确 UID，仍回退到全局 `display_name + source_user_id IS NULL` 查询并直接返回旧用户 ID，既没有建立新的 UID 身份，也没有安全的身份关联依据。
- [is_duplicate_message](../backend/app/importer.py) 对缺少源消息 ID 的消息按账号、群、`user_id`、时间及内容哈希去重。不同 UID 被合并成同一个 `user_id` 后，同秒同文就会被误判成重复。
- 即使源消息 ID 足以避免此次漏导，共用用户识别路径仍可能让成员归属/成员筛选错误；本轮实际执行并确认的是上述缺少源消息 ID 的 JSON 用例。未检查真实库是否存在这样的数据。
- 建议已知 UID 只能匹配相同 UID；不能仅凭昵称把已知身份挂到匿名用户。无 UID 历史与真实身份的合并应需要可靠证据，避免直接给旧记录补 UID 后把另一个同名用户再次混入。
- 验收覆盖先无 UID 后有 UID、两个不同 UID 同名、同 UID 改昵称、不同账号/群以及有/无源消息 ID 的去重；保留已有重复消息不重复入库的回归。
- 关联契约：[导入格式与去重](import-format.md)、[数据模型](data-model.md)。该诊断不读取真实 Cookie，不触发网络或采集。

### 修复结果（2026-10-21）

`ensure_user` 仅在没有 UID 时按无 UID 昵称回退；已知 UID 查不到就建立该 UID 的独立身份。新导入缺失/null/空字符串 UID 统一处理，无 UID 历史保持原归属。没有更改表结构，也未自动迁移真实旧用户或恢复此前可能漏导的消息。

新增 [test_import_user_identity.py](../backend/tests/test_import_user_identity.py) 8 项通过，覆盖 JSON/CSV、模拟 API 入库、不同 UID 同名、相同 UID 改昵称/旧昵称回填、跨账号及旧多群隔离、有/无源消息 ID、重复导入不增加消息、空 UID。7 项先出现业务失败（包括 3 条误成 2 条），修复后全部通过；同 UID 改昵称原本正确，保留绿灯回归。
