# TDD 开发规范与落地清单

本文件是本项目后续开发的持续规则，适用于修复、新功能、重构及 AI 辅助开发。目标是让已经验证的行为不因其他修改而退化，不承诺消除所有缺陷。

<!-- tdd-reminder:start -->
- 修改行为前先写失败测试（红），用最小实现通过（绿），再整理代码并重跑测试（重构）。
- 已有正常功能先补特征/回归测试；禁止为了制造红灯破坏用户数据或真实采集。
- 改完运行快速检查，交付前运行完整检查；测试零发现、失败、超时都不是通过。
- 不可通过删断言、跳过测试、提高复杂度基线或取消检查来消除红灯。
- 测试使用临时数据库、虚拟 Cookie、模拟微博响应；不得读取真实凭据或触发真实采集。
<!-- tdd-reminder:end -->

## 持续生效方式

1. 根目录 `AGENTS.md` 要求开发助手开始工作前完整阅读本文件。Codex 按项目目录发现该文件；它不是应用运行时，也不是每次对话都重新加载的保证。规则更新后应在本项目开始新任务，或明确要求当前任务重新阅读。
2. 前端 `npm --prefix frontend run dev` 与后端正常启动时，读取上面的提醒块并在终端打印。提醒不改变采集流程，不自动运行耗时检查。
3. `scripts/verify.py` 与 VS Code 任务提供真正的退出码检查；完整检查不通过就不能宣称交付完成。
4. CI 工作流可在 GitHub push/PR 中执行相同检查。只有远端启用分支保护并设置必需检查后，才会真正阻止不合格合并；本地文件不能自动赋予该权限。

规则发现依据：[OpenAI 官方 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。普通 Markdown 不会被 Python、Vite 或所有编辑器自动执行，所以提醒与检查需要显式接线。

## 五步实施范围

### 1. 保护关键业务行为

- 多账号、多群聊：只按账号筛选、只按群筛选、组合筛选及不匹配组合都不能串数据。
- 附件：全筛选结果的附件条数不同于含附件消息数；分页不改变汇总；软删除不混入普通列表。
- 消息类型：链接选项始终存在；链接筛选发出 `message_type=link`。
- 登录：后端保存 Cookie 后刷新账号准备状态；终态停止轮询，不要求重复手动导入。
- 采集：安全停止提交成功的当前页；失败页不推进断点；续传沿原任务、原断点；重复消息不重复落库。
- 回收站：软删除、恢复、彻底删除只影响所选范围；未确认拒绝执行；彻底删除不移除磁盘原件。
- 引用定位：后端从原引用消息确定查找内容；候选及上下文不能跨账号、群或删除状态，重复文本不能自动选择；关闭窗口保留原列表和删除范围，取消/超时后的迟到响应不覆盖页面。

### 2. 建立分层测试

- 后端业务层：保留已有 unittest，扩充边界断言。
- HTTP 层：真实 FastAPI 路由、参数校验、序列化和依赖注入，使用临时 SQLite；禁止启动真实 worker。
- 前端层：组件/纯函数/登录状态测试，模拟网络与时钟，不以构建成功代替功能验证。
- 浏览器层：隔离的本地页面及模拟 API，验证关键点击链；真实微博变化仍由单独的小范围人工验收判断。

### 3. 在测试保护下拆分与约束

- 优先拆出消息视图、共享消息模型、HTTP 客户端和登录轮询逻辑，不一次重写所有页面。
- 新模块不能反向依赖应用入口，共享层不能依赖功能层，禁止本地模块依赖环。
- 为已有大文件/复杂函数建立明确基线，只允许不增加；新模块采用更小上限。
- 重复代码检查与复杂度检查是机械预警，不等于代码质量的完整判断。不要机械地复制/搬迁大函数来躲门禁。

### 4. 用定向变异检验测试有效性

- 在隔离进程内故意遗漏账号筛选、把附件数误算为消息数、把续传游标改为 0、取消重复判定。
- 正常基线先通过；每个错误版本必须被预期业务断言识别。
- 导入错误、零测试、依赖缺失、异常退出或超时是检查错误，不得当成“测试杀死变异”。
- 存活变异导致失败，先判断测试缺口还是等价变异；禁止直接降低门槛。此处是有限的定向验证，不是全项目 100% 变异覆盖。

### 5. 形成可重复执行的交付流程

每个小改动依次经历：明确验收 → 失败测试 → 最小实现 → 代码整理 → 快速检查 → 完整独立进程检查 → 更新文档与实际证据。

- 同一个失败原因连续尝试三次仍无进展：停止扩大修改，记录证据、最小复现和所需决定。
- 交付写清执行命令、通过数、失败/未执行项；日志不含 Cookie、Token 或真实聊天内容。
- 检查脚本、测试、工作流、复杂度基线的变更单独解释，不由同一次功能实现随意放宽。
- 单人开发采用分阶段检查和独立子进程，不能将其描述成已有独立人员/独立 AI 审查。需要独立审阅时另行安排；默认不新增多代理或远端任务。

## 执行与验收记录

2026-09-07，五步的第一批实现已完成，本机完整检查通过。详细证据见 [本轮实施记录](tdd-implementation-record.md)。这不是全项目已达到完整测试覆盖的声明。

### 首次准备

在 VS Code 用“文件 → 打开文件夹”打开 `weibo-chat-collector` 根目录，而不是只打开 `frontend`。开发建议 Python 3.12、Node.js 22 或本机兼容版本，并安装 Chrome/Chromium/Edge。

在根目录的终端执行（本机本轮已安装，无需每次重装）：

```bash
.venv/bin/python -m pip install -r backend/requirements-dev.txt
npm --prefix frontend ci
npm --prefix browser-helper ci
```

没有 `.venv` 时先执行 `python3.12 -m venv .venv`。Windows 将解释器换成 `.\.venv\Scripts\python.exe`。开发依赖中的 `httpx` 用于 HTTP 测试，普通运行不强制安装。

### 在 VS Code 逐步操作

1. 打开 `docs/tdd-development.md`，确认本轮要改的行为和对应测试。
2. 按 macOS `⌘⇧P` / Windows `Ctrl+Shift+P`，输入 `Tasks: Run Task`（任务：运行任务）。
3. 选择 `TDD: 快速检查`，先确认当前基线为 `PASS`。它运行后端、检查脚本、浏览器助手、前端测试、类型/构建、结构检查，不启动真实微博采集。
4. 写一个最小失败用例。只跑对应测试，确认因所需行为不满足而失败；依赖缺失和语法错误不能作为 TDD 红灯证据。
5. 完成最小修复，重跑同一个测试，再整理代码。不要同时修改另一个无关功能。
6. 再选 `TDD: 快速检查`。修改前端时可另开 `TDD: 前端测试监听`，保存后自动重跑相关测试；终端 `Ctrl+C` 结束监听。
7. 交付前选 `TDD: 完整验收`。这还会运行定向变异及隔离浏览器测试；无需先开普通前后端服务，无需扫码。
8. 只有终端最后显示 `PASS` 且任务退出码为 0 才算本轮自动验收通过。失败时查看 `.tdd-results/fast/` 或 `.tdd-results/full/` 内对应日志，修复后重新运行，不删除失败测试。
9. 更新功能文档和实际验证记录；需要实机核验的操作单独标记，不能用模拟接口测试替代。

### 等价终端命令

```bash
# 每个小改动
.venv/bin/python scripts/verify.py --fast

# 交付前完整验收
.venv/bin/python scripts/verify.py

# 单独运行某一组，便于红—绿迭代
.venv/bin/python -m unittest discover -s backend/tests -p 'test_messages_http.py' -v
npm --prefix frontend test -- src/App.test.tsx
npm --prefix frontend run test:watch
.venv/bin/python scripts/mutation_check.py
```

`--fast` 不是“可以忽略失败”；它只省略浏览器与变异两项。完整检查不依赖普通 8000/5173 服务，用随机本地端口和独立浏览器用户目录。浏览器自动探测失败时设置 `TDD_CHROME_PATH` 为浏览器可执行文件绝对路径；测试不读取 `.env` 内的真实 Cookie 设置。沙箱环境若禁止本地端口/浏览器启动，需要批准该次本地检查，不能把权限失败当成测试通过。

### 文件分工和检查边界

- `frontend/src/main.tsx`：仅挂载应用。`App.tsx` 暂保留任务、工具和验证页的编排。
- `frontend/src/features/messages/`：消息工作区视图、筛选模型和测试。
- `frontend/src/features/login/`：会话轮询、Cookie 资料刷新和异步隔离测试；登录按钮动作仍由 App 编排。
- `frontend/src/shared/`：类型契约与 HTTP 客户端。
- `scripts/quality_check.py`、`frontend_quality.mjs`：静态本地依赖环/方向、文件行数、函数局部决策复杂度、完整函数体重复检查。
- `scripts/quality-baseline.json`：只存已有超限项和既有重复项；新文件默认不超过 400 行、新函数复杂度不超过 20。已有复杂函数不要求在本轮一次重写，但不能继续增加。`--snapshot` 只输出测量，不自动更新基线。
- 当前重复检查是完整函数体级别，不是通用片段克隆检测；静态依赖分析面向现有普通 Python/TypeScript 导入，不证明动态导入和运行时依赖不存在。
- `.tdd-results/`：本地生成日志与 JSON 结果，不入 Git；fast/full 分开保存，后续运行覆盖同模式报告。中断后报告可能停留 `running`，不能当成成功。
- 浏览器导出测试必须显式禁止落盘下载（`downloadBehavior.policy=deny`），不能向用户系统“下载”目录写测试文件。按用户要求，成功验证的固定模拟导出内容及时间记录在 [测试导出记录](test-export-records.md)；这会更新该 Markdown，但不记录真实聊天。仍检查实际 Blob 内容与导出范围，不能简单删除导出测试。

### CI 与后续扩展

`.github/workflows/tdd.yml` 已写好，安装依赖后执行同一完整检查并保存日志。本轮只完成本地验证，未推送、未在 GitHub 执行、未更改远端设置。

以后使用 GitHub 时，先确认 `TDD full check` 在远端跑通，再在仓库分支保护/规则集中设为必需检查，并限制绕过。检查脚本和工作流自身仍需受信任的审查；文件里的规则不构成防篡改系统。

后续每次需求继续补行为用例，逐步拆出采集监控、目标配置、删除流程等；增加相应 HTTP/浏览器失败路径。全量覆盖率门槛、全项目随机变异测试、独立审阅任务不是本轮已完成项。真实微博接口稳定性、账号 B、文件/视频和附件原件仍见 `docs/todo.md`。
