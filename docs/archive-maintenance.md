## 页面入口

选择账号与群聊后打开“本地归档”：

- 失败项保留原始访问链接，并在已捕获时显示实际失败的跳转地址。旧失败记录需重试一次才能记录实际地址。
- Fake-IP 失败旁的“设置此域名 HTTPS 兼容”会显示具体域名并要求确认，只为当前账号加入该精确域名。随后手动重试/恢复。明文旧地址升级为 HTTPS；证书、主机名、私网/回环地址检查继续生效，其他站点不接收微博 Cookie。域名设置不会自动解除暂停，也不保证源站允许访问。
- “重新下载此项”可将失败、等待处理、已跳过的项目重新排队；已保存/正在下载项不可这样重置，跨账号/群或已删除消息不可操作。暂停状态保持不变。
- “检查并补下载缺失或损坏文件”逐项校验本群已保存文件的大小和 SHA-256，只将异常项目重新排队并清除附件的已保存标记。大库检查可能耗时几分钟，原本暂停的群仍需手动恢复。只修复未删除消息，回收站内容可从备份恢复。
- 已保存图片在消息和详情中显示按需生成的缩略图；点击进入本地灯箱，可前后切换、左右方向键切换、原尺寸查看，Esc 关闭并返回原按钮。每个图片组对应当前消息。原图不压缩、不覆盖；缩略图是独立的 320 像素 JPEG 缓存。大像素/不支持格式无法生成缩略图时保留原图入口。

## 减少重复下载与断点续传

相同账号、相同群、相同资源类型和规范化 URL 的任务可复用已校验的本地原件。规范化去除锚点，并处理已支持域名的 HTTP→HTTPS 和微博外链包装；不随意删除签名参数或把所有 HTTP/HTTPS 地址等同。同一批不同时请求相同资源。规范化资源键建立索引，旧任务首次运行时补齐，避免每次下载扫描所有已保存资源。每条消息仍保留自己的任务、原始地址和本地入口，不跨群或删除状态复用快照；原有按账号的内容哈希文件去重保留。

图片、音频、文件和直链视频可在源站提供强 ETag 或 Last-Modified 时按字节续传。临时内容位于 `archives/<账号>/.resume-<任务>/`，使用 Range/If-Range。响应范围、最终地址、验证器和总大小必须匹配；服务器忽略 Range 返回完整 200 时重写文件，不拼接旧内容。源文件变化或范围失效时清理旧断点并重新下载；无验证器的资源重下完整文件。链接正文、HLS 暂不按字节续传。

网络中断和正常暂停可保留可续传内容，成功后移除。账号目录内另有最多 256 个固定锁条目，用于防止租约切换时两个进程同时写入同一续传文件；这些锁条目不进入备份。没有文件验证器、响应异常或超过上限的内容不会被标成保存成功。原有登录/限流暂停、最多三次临时错误尝试及磁盘余量保护继续生效。

## 视频与动态网页

新增支持未加密、带 ENDLIST 的 HLS 点播：最多两层清晰度列表、100 段，选择最低带宽版本以控制体积。支持 MPEG-TS 或单个初始化段的 fragmented MP4；所有分段逐跳执行相同地址与 Cookie 检查，段间至少间隔一秒，整个视频累计不超过 20 MiB。全部完成才发布本地视频。TS 格式能否直接在浏览器播放取决于浏览器，可使用本地播放器打开；不自动转码。

加密/DRM、直播、分离音轨、字节范围分段、不连续时间线、DASH 仍明确显示不支持，不保存不完整视频。第三方登录和远端脚本不会自动执行。

对于已经通过浏览器打开、但自动归档失败的网页，可点“导入网页正文”粘贴正文（至少 40 字，UTF-8 不超过 2 MiB）。保存的是明确标注“手动正文快照（不含关联媒体）”的纯文字快照，显示时转义，不执行粘贴脚本、不宣称图片视频已保存。此动作只处理选定的失败/等待处理/已跳过链接，不改变其他任务或账号暂停状态。

## 完整备份与恢复

归档窗口底部展开“备份、恢复与磁盘维护（全部账号）”。这是整个本地库的维护入口，不受当前群、日期或成员筛选限制。

创建备份前暂停全部群归档、停止采集并等待活动下载结束。点击“创建完整备份”后：

1. 校验所有已归档文件，缺失或损坏时先修复。
2. 持有数据库写入锁形成一致快照，打包数据库和附件目录。图片/视频等原件不重复压缩，数据库压缩；不包含独立的 `data/auth` 登录 Cookie 目录，续传临时文件也不打包。
3. ZIP 内含大小和 SHA-256 清单，校验通过后发布到数据库同级 `backups/archive-<随机ID>.zip`。页面显示实际路径。备份保留在本机，可另行复制到其他磁盘。

恢复时选择备份 ZIP：逐个校验路径、重复条目、大小和哈希，再校验 SQLite 数据库、引用原件。恢复到数据库同级 `restored/<随机ID>/`，包含 `database.sqlite3` 和 `attachments/`。现有库不覆盖；无效备份的临时目录自动清理。当前限制单包及解压总量最多 100 GiB、20 万条目，至少保留 256 MiB 磁盘余量。

确认新副本后切换使用：

1. 停止当前采集/下载并关闭后端，保留旧库。
2. 在 `.env` 中将 `DATABASE_PATH` 指向新目录的 `database.sqlite3`，将 `ATTACHMENTS_DIR` 指向新目录的 `attachments`。
3. 重启后端并刷新页面。恢复的采集任务为停止、归档为暂停；检查消息和图片后再自行恢复。新机器需要重新登录，备份不迁移 Cookie。

上传恢复和生成备份可能耗时较长，请保持页面打开。恢复阶段额外需要 ZIP 与解压副本空间；程序不会自动删除旧库或备份包。

## 磁盘清理

同一维护入口先点“预览可清理文件”，显示数量与空间。需要全部归档暂停且没有采集/活动下载。确认后再次计算清理范围，预览令牌不匹配则要求重新预览。

只处理：符合归档路径格式且没有任何任务/附件引用的原件、超过 24 小时的下载临时文件。仍被引用的文件（包括回收站、其他账号和共享原件）保留；拒绝符号链接根目录。清理是独立的显式操作，消息彻底删除仍只删除元数据，不自动删除文件。没有自动淘汰正常原件，也不自动删除备份。

## 新增接口与依赖

- `POST /api/archives/{id}/retry`：选定失败/等待/跳过项重新排队。
- `POST /api/archives/{id}/trust-host`：当前账号精确域名的 HTTPS Fake-IP 兼容。
- `GET /api/archives/integrity`：指定账号/群只读检查。
- `POST /api/archives/repair`：检查并重新排队异常文件。
- `POST /api/archives/{id}/snapshot`：显式导入纯文字快照。
- `GET /api/archives/{id}/thumbnail`：账号/群/删除态隔离的本地缩略图。
- `POST /api/archive-maintenance/backup`、`cleanup`、`restore`：全库维护。`cleanup` 首次不传令牌为预览，执行传预览 token；`restore` 接收 ZIP 原始请求体。
- 新表 `archive_failures` 保存实际失败地址，`archive_https_hosts` 保存账号的精确域名兼容设置，`archive_resource_keys` 为资源复用提供索引；创建幂等。
- 新增 Pillow 12.3.0 生成缩略图。升级环境执行 `.venv/bin/python -m pip install -r backend/requirements.txt`，然后重新加载后端。
